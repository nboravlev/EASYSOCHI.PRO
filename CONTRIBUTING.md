# Порядок работы над EASYSOCHI.PRO

Документ фиксирует, как мы ведём разработку в паре: кто что делает, что входит
в PR и как изменения проверяются перед попаданием в `main`.

## Цикл

```
1. Постановка задачи        → источник: бэклог в progress.md
2. Решение, коммит, PR      → ветка, описание с разделами проверки
3. Проверка на сервере      → сборка и три уровня контроля
4. Merge либо доработка
```

---

## 1. Постановка задачи

Задачи берутся из блока «План на обновление» в [progress.md](progress.md) —
он разбит на приоритеты «Высокий», «Средний», «Низкий».

- **один PR — одна задача**;
- находки, всплывшие по ходу другой работы, идут **в бэклог**, а не в текущий PR;
- выполненный пункт отмечается `[x]` в том же коммите, который его закрывает.

---

## 2. Разработка и PR

**Ветка.** От свежего `main`, префикс по смыслу: `fix/`, `feat/`, `chore/`,
`docs/`. В `main` не коммитим и не пушим напрямую.

**Один PR в работе за раз.** Стековые PR (база — не `main`, а другая ветка) —
только когда иначе никак. Тогда мержить строго по порядку и **обязательно с
удалением базовой ветки**: автоперенацеливание на `main` срабатывает у GitHub
только при удалении базы, иначе следующий PR вольётся не туда.

**Запись в протокол.** Каждый PR дописывает запись в `progress.md` в принятом
формате:

```
ГГГГ-ММ-ДД
*<ветка>

Что сделано:
- пункт
```

**Описание PR** содержит разделы:

| Раздел | Зачем |
|---|---|
| Что сделано | суть изменений |
| Что проверено | чем именно подтверждено |
| Что **не** проверено и почему | честная граница: на машине разработки нет запущенного демона Docker, сборку и рантайм проверить нельзя |
| Что проверить на сервере | конкретные команды и ожидаемый результат |
| Нужны ли изменения в `.env` | см. ниже |

**Переменные окружения.** Новые переменные **не приезжают с `git pull`** —
`.env` в репозитории нет. Если PR добавляет переменную, в описании должно быть
прямо сказано, что дописать в `.env` до пересборки. Значение по умолчанию в коде
предпочтительнее: тогда деплой не ломается, если про переменную забыли.

**Секреты в репозиторий не попадают.** Если секрет всё-таки попал — удаления из
индекса недостаточно, история публичная: **обязательна ротация**.

## 3. Проверка на сервере

Выполняется в рабочей копии `~/Projects/easysochi_pro/EASYSOCHI.PRO`.

> ⚠️ **Эта рабочая копия и есть прод.** Переключение на ветку PR означает
> выкладку непроверенного кода на боевой сайт. Проверять в спокойное время и
> держать откат под рукой (см. раздел 4).

### 3.1 Переключение на ветку PR

```bash
git status
```

Дерево должно быть чистым, иначе `git switch` откажется работать.

```bash
git fetch origin && git switch <ветка-PR>
```

Отдельную ветку создавать и вливать в неё код **не нужно** — ветка уже есть на
origin. Ответ `Switched to a new branch` означает, что создана локальная ветка,
а не что код новый: он пришёл из origin ровно тот, что в PR.

Если PR требует новых переменных — дописать их в `.env` **до** сборки.

### 3.2 Сборка и проверка

Один скрипт делает всё: предпроверки, сборку с тегом, запуск, ожидание
`healthy` и прогон проверок API.

```bash
./scripts/build.sh
```

Тег образов по умолчанию — короткий хеш текущего коммита, с суффиксом
`-dirty`, если в рабочем дереве есть незакоммиченные правки. Скрипт
дополнительно метит образы как `:latest`, поэтому обычный
`docker compose up -d` без переменных поднимает последнюю сборку.

Опции: `--tag <тег>` задаёт тег вручную, `--skip-tests` пропускает проверки
API, `--no-cache` пересобирает без кеша, `--help` показывает справку.

При любой неудаче скрипт сам печатает диагностику — `docker compose ps` и
последние 50 строк логов тех контейнеров, что не поднялись. Отдельно
собирать её руками не нужно.

Если собираете вручную, без скрипта, помните: строка `Built 0.0s` в выводе
**ненадёжна**, она бывает нулевой и при реальной пересборке. Достоверная
проверка — дата образа:

```bash
docker image inspect easysochi/contact-api easysochi/site easysochi/nginx --format '{{.RepoTags}} {{.Created}}'
```

Свежая дата должна быть у тех сервисов, чей **контекст сборки** затронут PR.
У остальных она законно останется старой.

### 3.3 Три уровня контроля

Первые два уровня скрипт закрывает сам: он не завершится успешно, пока
`postgres_db_easysochi`, `easysochi_site` и `easysochi_contact_api` не станут
`healthy`, а проверки API не пройдут целиком. Руками стоит посмотреть логи —
скрипт их не читает:

```bash
docker logs easysochi_contact_api --tail 50
```

Миграции применились (`[entrypoint] alembic upgrade head`), трейсбеков нет.

Третий уровень — то, что названо в разделе «что проверить на сервере» в
описании PR: обычно открыть страницу, проверить форму, посмотреть статистику.

Прогнать проверки API отдельно от сборки:

```bash
docker exec -i easysochi_contact_api python3 - < easysochi-backend/app/test/check_payment_api.py
```

## 4. Решение

### Всё поднялось

1. Merge на GitHub **с галочкой удаления ветки**;
2. локальная уборка:

```bash
git switch main && git pull --prune
```

```bash
git branch -d <ветка-PR>
```

`--prune` убирает ссылку на удалённую ветку, `-d` строчной откажется удалять
неслитую ветку — это страховка от потери работы.

Пересобирать после возврата на `main` не нужно: код там идентичен тому, что уже
работает.

### Не поднялось

Откат:

```bash
git switch main && ./scripts/build.sh
```

Если PR содержал миграцию, простого возврата на `main` мало — сначала
откатить схему, иначе старый код обратится к изменённым колонкам:

```bash
docker exec easysochi_contact_api alembic downgrade -1
```

Быстрая альтернатива без пересборки, если образ предыдущей сборки ещё на
диске, — поднять его по тегу:

```bash
TAG=<хеш-предыдущего-коммита> docker compose up -d
```

Затем прислать в тикет или в чат полный вывод `./scripts/build.sh` —
диагностику он печатает сам.

**Не чинить молча.** Если правка всё-таки сделана руками — сказать, что именно
изменено, иначе следующий PR ляжет на другой код.

## Грабли, на которые уже наступали

Короткий список, чтобы не проходить это дважды.

- **`.dockerignore` не рекурсивен**, в отличие от `.gitignore`: `__pycache__`
  совпадает только с каталогом в корне контекста, для вложенных нужен `**/`.
  И читается он из корня **контекста сборки**, а не репозитория.
- **Docker пишет правила в iptables мимо `ufw`.** Опубликованный порт доступен
  из интернета, даже если файрвол закрыт. Поэтому у БД указан `host_ip`:
  `127.0.0.1:${POSTGRES_PORT}:5432`.
- **Файл без перевода строки в конце.** Дописывание через `>>` склеивает новую
  строку с последней. Так `.gitignore` получил нерабочий паттерн
  `progress.md.htpasswd`, и `.htpasswd` с хешем утёк в публичный репозиторий.
- **`.htpasswd` не хранится в репозитории.** На новом сервере его нужно создать
  **до** первого `docker compose up`, иначе Docker создаст на месте bind-mount
  директорию и nginx не поднимется. См. шаг 3 в [README](README.md).
- **DBeaver кеширует SSH-туннель** между попытками и не подхватывает изменённые
  настройки на лету. При ошибке «программа на вашем хост-компьютере разорвала
  установленное подключение» первым делом полностью перезапустить клиент.
- **Проверки API — это скрипт, а не pytest-набор.** Раньше файл назывался
  `test_payment_api.py`, pytest подбирал его по имени и показывал `FAILED`
  даже при нулевом коде возврата, потому что скрипт завершается через
  `sys.exit()`. Сейчас файл называется `check_payment_api.py`, функции —
  `run_checks` и `manual_webhook_check`, и pytest его не видит. Не
  переименовывайте обратно.
